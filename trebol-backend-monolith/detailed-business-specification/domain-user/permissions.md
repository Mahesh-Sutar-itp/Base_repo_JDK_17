# Identity & Access (`user`) — Permissions

This domain **owns** the authorization model for the entire system. Everything in
`domain-customer/permissions.md`, `domain-salesperson/permissions.md` and
`domain-product/permissions.md` is an application of what is specified here.

---

## 1. The model in four tables

```
app_users ──one role──▶ app_user_roles ──grants──▶ app_user_role_permissions ──▶ app_permissions
                                                                                      │
                                                                          permission_code
                                                                                      │
                                                                                      ▼
                                                              SimpleGrantedAuthority ──▶ hasAuthority('...')
```

**Authorities are not roles.** A user has exactly one role (BR-USER-002); the role is
granted a set of permissions; the permission **`code`** becomes a granted authority; and
`@PreAuthorize("hasAuthority('...')")` matches that code. **Nothing in the entire codebase
ever checks a role name** — except `RegistrationServiceImpl`, which looks up the hardcoded
`"Customer"` role to assign it (BR-USER-011).

Codes follow a `resource:action` convention (BR-USER-031) and are unique
(BR-USER-006). `Permission.code` is `@Size(min = 1, max = 25)`, and the longest seeded
code — `product_categories:update` — is **exactly 25 characters**, i.e. at the ceiling.

## 2. The eight user-domain authorities

All resolve through `AuthorityCodes` in the **shared-contracts module**, never as string
literals. Gate B requires zero `hasAuthority('...')` literals anywhere; exit criterion
**X6** pins it.

| Constant | Value (verbatim) | Guards |
|---|---|---|
| `USERS_READ` | `users:read` | `GET /data/users` |
| `USERS_CREATE` | `users:create` | `POST /data/users` |
| `USERS_UPDATE` | `users:update` | `PUT /data/users` |
| `USERS_DELETE` | `users:delete` | `DELETE /data/users` |
| `USER_ROLES_READ` | `user_roles:read` | `GET /data/user_roles` |
| `USER_ROLES_CREATE` | `user_roles:create` | `POST /data/user_roles` |
| `USER_ROLES_UPDATE` | `user_roles:update` | `PUT /data/user_roles` |
| `USER_ROLES_DELETE` | `user_roles:delete` | `DELETE /data/user_roles` |

BR-USER-049: account and role administration require **explicit** authorities — there is
no implicit grant and no role shortcut.

## 3. The grant matrix — seeded, and seeded only

`src/main/resources/data.sql` seeds **4 roles, 54 permissions and 100 grants**:

| `user_role_id` | Role | Grants | Meaning |
|---|---|---|---|
| 1 | `Administrator` | **54** | every authority in the catalogue |
| 2 | `Manager` | **31** | |
| 3 | `Salesperson` | **14** | |
| 4 | `Customer` | **1** | just `checkout` — the role self-registration assigns (BR-USER-011) |

**BR-USER-038 — grants are seed data only.** There is no runtime API to grant or revoke:
`PermissionsRepository` is empty, `UserRolePermissionsRepository` declares only a read
query, and both join columns are `updatable = false` (BR-USER-008). Changing who can do
what requires a database change.

The identity-generator restarts that **must** accompany the seed data, verbatim:

```sql
ALTER TABLE `app_user_roles` ALTER COLUMN `user_role_id` RESTART WITH 5;
ALTER TABLE `app_permissions` ALTER COLUMN `permission_id` RESTART WITH 55;
```

Omit either and the first insert collides with a seeded row.
`app_user_role_permissions` needs **no** restart, because its grant rows do not specify
the primary key — the insert lists only `(permission_id, user_role_id)`.

### 3.1 Load order

`app_user_roles` and `app_permissions` **before** `app_users` and
`app_user_role_permissions`; `people` before `app_users`.

### 3.2 Bootstrap accounts — NOT carried forward (G7, X10)

The monolith's `data.sql` also seeds four accounts, with the comment
*"passwords equal usernames, bcrypt logarithm cost factor of 10"*:

| id | `user_name` | role |
|---|---|---|
| 1 | `admin` | Administrator |
| 2 | `manager` | Manager |
| 3 | `salesperson` | Salesperson |
| 4 | `customer` | Customer |

plus `ALTER TABLE app_users ALTER COLUMN user_id RESTART WITH 5;`

**This is BR-USER-055 — "bootstrap credentials are committed to source control" — and it
is exactly what invariant G7 forbids replicating.** Copying it into a new service would
put demonstration credentials for the all-54-authority `Administrator` role into committed
configuration in a second place.

**Phase 2 decision, approved by the project owner:**

| | |
|---|---|
| `data.sql` in identity-service | seeds **only** the 4 roles, 54 permissions and 100 grants, with the two restart statements. **No `app_users` row, and no `user_id` restart.** |
| The four accounts | recreated in `src/test/resources` as a **test fixture**, under a `TEST FIXTURE` banner, so every ported test keeps working unchanged (G3, G8) |
| First administrator | created by an operator from the environment; the step is recorded in `microservices-conversion/baseline/PHASE-2-EXIT.md` |
| New runtime code | **none** — no bootstrap component, no conditional seeding |

This is a **deliberate, recorded deviation** from the baseline, tracked in `00` §6
alongside the transactional-registration deviation. The monolith's own `data.sql` is
**not** modified in Phase 2 — the monolith keeps serving all 67 routes until Phase 4.

## 4. Enforcement — and the Gate D consequence

### 4.1 Two layers, where they exist

```java
@RequestMapping("/data/users")
@PreAuthorize("isAuthenticated()")                        // class level — layer 1
public class DataUsersController ... {
    @GetMapping
    @PreAuthorize("hasAuthority('" + USERS_READ + "')")   // method level — layer 2
```

1. **Class level — `isAuthenticated()`** → anonymous requests get **401**.
2. **Method level — `hasAuthority(...)`** → authenticated-but-unauthorised gets **403**.

### 4.2 The finding: there is no third layer

**`SecurityConfig` declares no `authorizeHttpRequests` rules at all** (BR-USER-025).
Enforcement is **entirely** method-level, which means:

> **Any endpoint without an authority annotation is publicly reachable.**

And `JwtTokenVerifierFilter` lets a header-less request **through** the chain
unauthenticated rather than rejecting it — so there is no implicit gate either.

**Consequences recorded in `ADR-002` (Gate D):**

- **A gateway cannot derive authorization from paths.** There are no path rules to mirror.
- **The decision is therefore:** shared signing key, **local verification per service**,
  method-level enforcement retained in each service, gateway for routing and TLS only.
- **Every service must keep its `@PreAuthorize` annotations**, because they *are* the
  policy. Catalogue already works this way; its `SecurityConfig` is verify-only.
- **Identity is the only token issuer.** No other service reads `app_users`.

### 4.3 The route surface, by enforcement level

| Route | Enforcement | Rule |
|---|---|---|
| `POST /public/login` | **none** — a filter, not a route | BR-USER-014 |
| `POST /public/guest` | **none** — a filter, not a route | BR-USER-026 |
| `POST /public/register` | **none** — fully anonymous, no `@PreAuthorize` on the class | — |
| `GET`/`PUT /account/profile` | `isAuthenticated()` **only, no authority** | **BR-USER-050** |
| `GET /access`, `GET /access/{apiRoute}` | `isAuthenticated()` only | BR-USER-034, BR-USER-035 |
| `/data/users/**`, `/data/user_roles/**` | both layers | BR-USER-049 |

**BR-USER-050 is correct and must not be "tightened".** `/account/profile` takes the
identity from `principal.getName()`, never from the request, so there is no horizontal
privilege path — and requiring `users:update` would break self-service for ordinary
customers, who hold only `checkout`.

**`IdentityRouteParityTest` must assert all of the following**, because each is a silent
breakage if lost:
- the exact authority **value** per method on both data controllers;
- the class-level `isAuthenticated()` on both data controllers and on `AccessController`;
- `/account/profile`'s `isAuthenticated()`-**only** model;
- `/public/register` being **unsecured**;
- `/public/login` and `/public/guest` being **filter-processed URLs wired in
  `SecurityConfig`**, not controller mappings;
- that **no `/account/password` route is invented** (register item **D15**).

## 5. How authorities reach a request

### 5.1 At login (Identity only)

1. `DaoAuthenticationProvider` → `UserDetailsServiceImpl.loadUserByUsername`
2. `findByNameWithRole` — the `JOIN FETCH` is **required**, the relation is LAZY
3. `UserPermissionsServiceImpl.loadPermissionsForUser` →
   `deepFindPermissionsByUserRoleId` → collected into a **`HashSet<Permission>`**
4. codes → `SimpleGrantedAuthority`
5. `GenericJwtAuthenticationFilter` writes them into the **`authorities`** claim and
   returns the token in **both** the header and the body (BR-USER-016)

**The `HashSet` is the in-memory de-duplication of BR-USER-007.** Phase 0's **D17** added
`UQ_UROLEPERMS_UROLE_PERM` so the database now rejects duplicate grants, and the
de-duplication was **deliberately left in place**. Both port. The **guest** path does
**not** de-duplicate — it collects a plain list.

### 5.2 On every subsequent request (every service)

`JwtTokenVerifierFilter` reads the `authorities` claim, builds
`SimpleGrantedAuthority` from each entry's **`"authority"`** key, and populates the
security context. **No database lookup, in any service** (BR-USER-022).

Two strings are **wire contract across all services** and must be byte-identical
everywhere: the claim name **`"authorities"`** and the per-entry key **`"authority"`**.
Change one in one service and every token breaks.

**The security consequence (BR-USER-022 + BR-USER-017):** a revoked grant stays effective
until the token expires, and lifetime is the **sum** of the three configured components.
`00` §2 W3 records it; it is not fixed in Phase 2.

### 5.3 Guest authorities

`loadGuestUserDetails()` reads `securityProperties.getGuestUserRoleId()` and grants that
role's permissions (BR-USER-030). The guest's **username and password are both**
`guestUserName` (BR-USER-026) — D14 remainder (a), ruled **PRESERVE**: the configured guest
name *is* the stored credential `DaoAuthenticationProvider` matches, and it is seeded.
Replacing it is a credential/product decision with a client-visible effect, not conversion
work. Guest access is **disabled by default** (BR-USER-027).

## 6. Authority discovery — what `/access` tells a client

| Endpoint | Returns | Mechanism | Rule |
|---|---|---|---|
| `GET /access` | `routes` | `authority.replaceAll(":.+$", "")` | BR-USER-032 |
| `GET /access/{apiRoute}` | `permissions` | `if (authority.contains(apiRoute))` then `replaceAll("^.+:", "")` | **BR-USER-033** |

**BR-USER-033 matches by substring, not equality**, so `GET /access/product` returns the
actions of `products:*`, `product_lists:*` **and** `product_categories:*`.

**Revisited in Phase 2 as the register required; the ruling is still PRESERVE.**
`AuthorizedApiServiceImplTest` asserts the current behaviour, so clients may depend on it.
The catalogue now makes exact matching a one-line change, but making it is a
**client-visible contract change** (G1, G2) needing its own ruling and release note.
Recorded as a post-conversion backlog item.

Neither endpoint reads the database — both work off the authorities already on the
`UserDetails`, which came from the token.

## 7. Known gaps in the model, all preserved

| Rule | Gap |
|---|---|
| BR-USER-036 | **Four seeded authority codes are dead** — never referenced by any annotation |
| BR-USER-037 | **Several seeded read authorities are never enforced** on the routes they appear to describe |
| BR-USER-038 | **No runtime grant/revoke API** — the matrix is a database change |
| BR-USER-023 | **All four account-status flags are hardcoded `true`** — an account cannot be locked, expired or disabled (register item **D15**) |
| BR-USER-004 | **One person, at most one account is enforced on the profile path only** — not on either create path, and with no database constraint (`00` §2 W1) |

All 54 codes stay in the catalogue regardless of whether anything enforces them: the
catalogue is generated from the seed data, and `CATALOGUE_SIZE 54` plus the checksum are
asserted by `AuthorityCatalogueIntegrityTest` (G2, X6).

## 8. Porting checklist

| Item | Requirement |
|---|---|
| Authority source | `AuthorityCodes` consumed from `trebol-shared-contracts`; **zero** `hasAuthority('...')` literals in identity-service source (Gate B, X6) |
| Annotations | Every class-level and method-level `@PreAuthorize` ported verbatim, including `/account/profile`'s `isAuthenticated()`-only model and `/public/register`'s absence of any |
| Filters | `/public/login` and `/public/guest` ported **as filters**, with the exact `SecurityConfig` wiring order (login → guest → verifier) |
| Wire contract | `"authorities"` claim name, `"authority"` entry key, `"Bearer "` prefix — byte-identical to every other service |
| Signing key | one shared `SecretKey` per `ADR-002`, built by `JwtKeyConfig` from `${TREBOL_JWT_SECRET_KEY}` with **no default** (G7, X10) |
| Seed data | 4 roles + 54 permissions + 100 grants + the two restart statements. **No bootstrap account row** (§3.2) |
| Pinning tests | `IdentityRouteParityTest` (§4.3) and `NoAuthorityLiteralsArchitectureTest` with its own count floor |
| Literals | all eight `users:*` / `user_roles:*` values unchanged (G2) |
